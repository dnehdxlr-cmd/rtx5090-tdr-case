# RTX 5090 GPU-loss / TDR case report

[English overview](README.en.md) · [한국어 조사 기록](README.md)

**Observed outcome:** On 10 November 2026, a replacement RTX 5090 reproduced GPU loss and a new full live dump with code 0x117 on driver 621.01. After backing up and resetting three CUDA/DirectX disk caches and rebooting, one run of the same short workload sequence completed without a new monitored GPU event. This does not establish cache corruption as the root cause, a permanent fix, or a healthy graphics card.

Prepared for sharing on 23 November 2026 from records collected on 10 November. No follow-up stability evidence was collected for 11–23 November. Times below use KST (UTC+9); the preserved CUDA JSONL files use UTC.

## Context and incident sequence

The owner reported similar black screens and GPU loss before replacing the card with the same model. Tests and normal use were satisfactory after replacement, followed by the November recurrence. The exact replacement date was not established. This is not evidence of a continuous fault immediately after replacement.

Driver 621.14 was installed on 6 November. The owner had not recently run AI workloads after that update. The trigger of the 10 November daytime incident remains unknown; it should not be assumed to have been the later cuDNN test.

At 16:04:37, nvlddmkm logged a UCodeReset TDR. A 0x117 live dump followed at 16:05:03, a 0x193 graphics diagnostic dump at 16:06:54, and a 0x7F/8 double-fault system crash dump at 16:07:22. The last dump showed repeated NVIDIA recovery frames and kernel stack exhaustion. This identifies a subsequent recovery-path failure, not the cause of the initial GPU hang.

After rollback to 621.01, the bounded cuDNN attention probe stopped making progress, reported a CUDA unknown error and left the GPU inaccessible. The owner confirmed the black-screen recurrence and forced a power cycle. A new full 0x117 live dump, subsequent WER 141/1B8 reports and an `nvidia-smi` GPU-lost response corroborated the failure.

## Comparison workload and environment

Both comparison runs used the active NVIDIA driver 621.01 / 32.0.16.2101, HAGS enabled, TdrDelay 8, TdrLevel 3, and a 600 W power limit. Recorded Windows build: 10.0.26300.9818. The existing runtime was PyTorch 2.13.0+cu130, CUDA 13.0, cuDNN 9.20 (92000), compute capability 12.0. No packages were installed for these tests.

The suite order was H.264 NVENC encode, NVIDIA D3D11 decode, exact CPU↔GPU transfer verification, BF16 matrix multiplication, then cuDNN BF16 attention. Attention used Q/K/V shape `[1,56,16384,128]`, noncausal operation, dropout 0 and only `SDPBackend.CUDNN_ATTENTION`. The CUDA workload file was byte-identical across runs, SHA-256:

`C119A98DF9339448568409564B2F4732A03D3574F7ED24B745EA29012B57B3A3`

| Workload | Before cache reset | After cache reset + reboot |
|---|---|---|
| NVENC 1080p60 H.264 | 30 seconds, exit 0 | 30 seconds, exit 0 |
| NVIDIA D3D11 decode | 30 seconds, exit 0 | 30 seconds, exit 0 |
| 256 MiB exact transfer | 15.031 s, 221 iterations | 15.041 s, 232 iterations |
| 8192×8192 BF16 matmul | 45.004 s, 5,898 iterations | 45.000 s, 5,802 iterations |
| cuDNN BF16 attention | Last progress at 35.308 s / 954 iterations; subsequent CUDA error, GPU loss and 0x117 | 45.024 s / 1,227 iterations, exit 0 |

The last progress timestamp is not an exact onset time. Process duration differs from the workload loop time. Iteration counts are not a controlled performance comparison.

The before-run attention process started at 21:56:10.209. Its last progress record was at 21:56:47.227. The full 0x117 dump timestamp was 21:57:29.358; the Python CUDA error was logged at 21:57:31.573. At 21:59:45, `nvidia-smi` returned exit code 6 and “GPU is lost.” The next boot was at 22:06:24 after a forced power cycle. There was no repeat load with the original caches after that boot.

The after-run suite started at 23:03:04.216 and finished its loads around 23:06:34. The observer then monitored delayed events for 120 seconds. The suite completed at 23:08:34.786. A final check at 23:10:35 returned the GPU normally. No new 117, 141, 193, 1B8, BlueScreen or selected System GPU/WHEA warning/error was found in the monitored window. Recorded temperatures and power were spot readings before/after workloads, not in-test peaks.

## Cache intervention and other state changes

The original CUDA ComputeCache, NVIDIA DXCache and Windows D3DSCache were backed up locally. NVIDIA service/overlay restart was used to release a CUDA cache lock, and the components were restored. Locked directories were moved to backup early in an approved normal reboot. The resulting boot timestamp was 22:55:13.5. Before the next test, live cache directories contained no files with pre-boot modification times; normal desktop startup had already generated some fresh files.

The retained logical file lengths were 1,991,680,050 bytes for the original CUDA cache, 8 additional pre-boot regenerated bytes, 31,736,401,920 bytes for DXCache, and 4,413,861,888 bytes for D3DSCache. These are logical lengths, not allocated disk usage. Four D3DSCache WAL/SHM sidecar files from the pre-boot inventory were absent after shutdown/reboot; the remaining main files matched in existence and length. No claim of bytewise verification of all cache contents is made.

The observer was improved to collect delayed WER events, include 1B8, query GPU health after failure, and avoid further loads after failure. Workload order, duration and inputs were unchanged. There was no continuous GPU-state polling during a load.

## Dump findings and interpretation limits

The new full live dump was classified by CDB as `VIDEO_TDR_TIMEOUT_DETECTED (117)` and `LKD_0x117_IMAGE_nvlddmkm.sys`, in the System process. The loaded NVIDIA image matched the verified 621.01 driver. The selected Windows stack includes `VidSchiCheckHwProgress`, `VidSchiReportHwHang`, `TdrIsRecoveryRequired` and `TdrCollectDbgInfoStage1`.

The same generic CDB bucket and substantial Windows scheduler-stack similarity were found in the daytime 621.14 dump. These are evidence of a shared TDR class, not proof of the same underlying defect. NVIDIA private recovery-context symbols were unavailable. An export name followed by a large offset is not a reliable identification of the originating NVIDIA function.

WER 141 referred to a separate dump from the full 0x117 file. Initial immediate result JSON contained an empty event list because WER was logged later. NVIDIA and AMD 1B8 records used a display-diagnostic path; they do not establish two failed GPUs or an AMD root cause. The later reproduction did not establish recurrence of the daytime 0x7F/8 stack-exhaustion crash.

Important unresolved variables:

1. The failing 621.01 run was performed after driver replacement but before an OS reboot. The passing run followed power-cycle recovery, cache intervention and another reboot. There is no old-cache/reboot-only control.
2. All three cache groups were reset together. Cache effects cannot be separated from one another or from GPU/driver state reset by reboot.
3. Only one bounded post-intervention pass was collected. No cache restoration, extended stress test or repeated warm-cache series was performed.
4. NVIDIA `AfterInstall` error **0x80070005 remains unresolved**. Active core driver files and HD Audio 1.4.6.6 were verified, but full installer success was not established.
5. The pre-replacement direct-cuDNN frontend fixed engine plan was not the same execution route as this PyTorch SDPA test. The old raw dumps were unavailable. Exact identity of the pre- and post-replacement defect remains unknown.
6. The first faulty kernel, driver-only causation, hardware fault, power/PCIe fault and long-term resolution are not established by this evidence.
