# RTX 5090 블랙스크린·GPU lost 조사 기록

**한국어** | [English](README.en.md)

**2026년 11월 10일, 교체받은 RTX 5090에서 GPU 이탈과 0x117이 재현됐다. 이후 CUDA·DirectX 캐시를 백업·초기화하고 재부팅한 뒤, 같은 짧은 시험을 한 차례 통과했다.** 캐시가 원인이었다거나 문제가 완전히 해결됐다고 확정한 결과는 아니다.

이 자료는 11월 10일의 로컬 조사 기록을 **11월 23일 공유용으로 정리**한 것이다. 11월 11~23일의 추가 사용·안정성 자료는 수집하지 않았다. 본문의 시각은 KST(UTC+9), 첨부 CUDA JSONL의 시각은 UTC다.

## 경과

- 교체 전에도 CUDA 연산 중 블랙스크린과 `GPU is lost`가 발생했다. 사용자는 같은 모델로 교체한 뒤 테스트와 실제 사용이 정상이었다고 확인했다. 정확한 교환일은 특정하지 않았다.
- 11월 6일 드라이버가 621.14로 바뀌었다. 사용자는 업데이트 이후 최근 AI 작업을 하지 않았다고 설명했으며, 11월 10일 오후 최초 장애의 촉발 작업은 확인하지 못했다.
- 11월 10일 오후에는 화면 신호 단절·원격 연결 종료·팬 고속 회전이 보고됐다. 0x117과 0x193 진단 덤프 이후 0x7F/8 시스템 충돌 덤프에서 NVIDIA 복구 경로의 반복 호출과 스택 고갈을 확인했다. 이것이 최초 GPU 정지의 원인까지 특정하지는 않는다.
- 같은 날 621.01로 롤백한 뒤, cuDNN 어텐션 시험에서 CUDA 오류·GPU lost·새 0x117이 재현됐다. 사용자가 전원을 강제로 껐다 켰다.
- CUDA ComputeCache, NVIDIA DXCache, Windows D3DSCache를 보존하고 초기화했다. 이후 정상 재부팅과 같은 시험을 수행했으며, 이 한 차례에는 장애가 재현되지 않았다.

자세한 시각은 [타임라인](data/timeline.csv), 영문 설명은 [REPORT.en.md](REPORT.en.md)에 정리했다.

## 같은 시험의 이전·이후 결과

| 시험 | 캐시 초기화 전, 621.01 | 캐시 초기화·재부팅 후, 621.01 |
|---|---|---|
| H.264 NVENC 1080p60 인코딩 | 30초 완료 | 30초 완료 |
| NVIDIA D3D11 하드웨어 디코딩 | 30초 완료 | 30초 완료 |
| 256MiB CPU↔GPU 전송·바이트 비교 | 15.031초, 221회 완료 | 15.041초, 232회 완료 |
| BF16 8192×8192 행렬곱 | 45.004초, 5,898회 완료 | 45.000초, 5,802회 완료 |
| cuDNN BF16 어텐션 | 35.308초·954회까지 진행 기록 후 정지, CUDA 오류·GPU lost·0x117 | 45.024초·1,227회 완료 |

35.308초는 **마지막 정상 진행 로그의 경과 시간**이다. 최초 고장 시각의 정확한 측정값이 아니다. 반복 횟수 차이를 성능 개선의 증거로 해석하지 않는다.

후속 시험은 23:03:04~23:06:34에 수행했고, 부하 종료 뒤 120초 동안 지연 이벤트를 추가 관찰했다. 23:10:35 최종 조회에서 GPU가 정상 응답했으며, 감시 범위 내 새 117·141·193·1B8·BlueScreen 및 System GPU/WHEA 경고·오류는 확인되지 않았다. 이 관찰창 밖의 안정성을 보증하지 않는다.

## 시험 조건과 실제 변경 사항

비교 시험의 활성 드라이버는 621.01 / 32.0.16.2101이다. HAGS ON, TdrDelay 8, TdrLevel 3, 전력 상한 600W를 유지했다. 기존 PyTorch 2.13.0+cu130, CUDA 13.0, cuDNN 9.20을 사용했으며 새 패키지는 설치하지 않았다. Windows는 조사 당시 10.0.26300.9818로 기록됐다. 자세한 값은 [환경 데이터](data/environment.json)에 있다.

어텐션 조건은 BF16 Q/K/V `[1,56,16384,128]`, noncausal, dropout 0, `SDPBackend.CUDNN_ATTENTION`이다. CUDA 부하 스크립트는 이전·이후 SHA-256이 동일하다. 감독 코드는 뒤늦게 생성되는 WER 수집과 실패 후 상태 확인을 보완했지만, 부하 순서·입력·시간은 유지했다. 시험 중 반복 GPU 상태 조회는 하지 않았다.

CUDA 캐시 잠금 해제를 위해 NVIDIA 서비스와 오버레이를 잠시 재시작했고 복구했다. 잠긴 DirectX 캐시는 승인받은 재부팅 때 기존 디렉터리를 백업으로 이동해 초기화했다. 새 부팅은 22:55:13.5이며, 시험 직전 활성 캐시 폴더에 부팅 전 수정 시각의 파일이 없음을 확인했다. 원본 캐시는 로컬에 보관했고 이 공유 자료에는 포함하지 않았다.

백업의 파일 길이 합계는 CUDA 약 1.99GB, NVIDIA DXCache 약 31.74GB, Windows D3DSCache 약 4.41GB였다. 이는 실제 디스크 할당량이 아니며, 크기나 오래된 파일의 존재만으로 손상을 판정하지 않는다. D3DSCache 사전 목록의 WAL/SHM 보조파일 4개는 종료·재부팅 후 백업에 없었고, 나머지 본체 파일은 존재와 길이를 확인했다. [캐시 검증 요약](data/cache-reset.json)을 참고할 수 있다.

## 확인한 것과 아직 구분하지 못한 것

새 덤프의 CDB 분류는 `VIDEO_TDR_TIMEOUT_DETECTED (117)`, `LKD_0x117_IMAGE_nvlddmkm.sys`다. WER 141과 1B8도 뒤늦게 기록됐다. 초기 시험 JSON의 `Events: []`만으로 GPU 장애가 없었다고 해석하면 안 된다. [선별한 덤프·GPU lost 발췌](evidence/diagnostic-excerpts.txt)에 정리했다.

다음 제한이 남아 있다.

- 이전 실패는 드라이버 교체 후 OS 재부팅 전 시험이다. 이후에는 강제 전원 재시작과 캐시 초기화 후 정상 재부팅이 있었다. **기존 캐시를 유지한 채 같은 재부팅만 수행한 대조 시험이 없다.**
- CUDA와 두 DirectX 캐시를 함께 초기화했다. 어느 캐시의 효과인지, 재부팅으로 GPU·드라이버 상태가 초기화된 효과인지 분리하지 못했다.
- 한 차례의 짧은 통과다. 장기 사용, 캐시 재축적 후 반복 시험, 원래 캐시 복원 시험은 하지 않았다.
- NVIDIA 설치 후처리의 **AfterInstall 0x80070005는 미해결**이다. 활성 핵심 드라이버와 오디오 1.4.6.6은 확인했지만 설치 전체가 정상 완료됐다고 주장하지 않는다.
- 교체 전 직접 cuDNN frontend의 고정 엔진 계획과 이번 PyTorch cuDNN 경로는 동일 실행이 아니다. 교체 전 원본 덤프도 없어 같은 결함인지 확정하지 못했다.
- 일반적인 TDR 버킷·Windows 스케줄러 스택의 유사성만으로 드라이버 버그, 카드 불량, 전원·PCIe 문제를 구분할 수 없다. 시험 중 최고 온도나 전력도 측정하지 않았다.
